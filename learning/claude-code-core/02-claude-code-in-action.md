## Learning objectives

By the end of this document you should understand *why* tool use is what
turns a language model into a coding assistant at all, manage context
deliberately across a long session, build custom commands and hooks, and
know what the Agent SDK is for.

## Why a coding assistant needs "tool use" at all

A language model on its own only processes and returns text — ask a raw
model to read a file and it will tell you it can't. A coding assistant
solves this with **tool use**: the assistant appends instructions to your
request teaching the model how to *request* an action (e.g., "respond with
`ReadFile: name`"), then the assistant itself executes that request and
feeds the real result back in. The model still never touches your
filesystem directly — it generates carefully formatted text, and the
harness around it does the actual reading, writing, and running. Claude's
particular strength at tool use (combining unfamiliar tools effectively,
adapting as new ones are added) is what lets Claude Code navigate a
codebase without needing to index or upload it wholesale — a real security
and privacy advantage, not just a convenience.

The three-step loop underneath any real task mirrors how a human developer
would work: **gather context** (what's affected, what's relevant),
**formulate a plan** (what changes, what to verify), **take action** (edit
files, run commands) — the first and last steps are exactly where tool use
does the work a text-only model couldn't.

## Persistent project memory in practice: CLAUDE.md and `@` mentions

Running `/init` in a new project has Claude analyze the whole codebase —
purpose, architecture, key commands, coding patterns — and write the
result to `CLAUDE.md`, which then gets included in *every* request for
that project, functioning as a persistent system prompt. There are
actually three recognized locations, each with a different scope:
`CLAUDE.md` (generated by `/init`, committed, shared with the team),
`CLAUDE.local.md` (personal, not shared), and `~/.claude/CLAUDE.md`
(applies to every project on your own machine). Editing `CLAUDE.md`
directly — or running `/memory` to open it inside a session — is how you
correct a recurring annoyance permanently rather than repeating the same
correction every conversation.

The `@` symbol pulls a specific file into the current request directly
("How does the auth system work? `@auth`"), and the same syntax works
*inside* `CLAUDE.md` itself for a file relevant across most of the
project (a database schema, say) — its contents then get included
automatically on every request instead of Claude having to search for and
re-read it each time. If a repo already has an `AGENTS.md` for another
tool, adding `@AGENTS.md` as the first line of `CLAUDE.md` imports it
rather than duplicating instructions.

## Making changes: screenshots, Planning Mode, and effort level

**Screenshots** (paste with `Ctrl+V`, even on macOS) are often the most
precise way to point Claude at a specific visual element you want changed
— faster and less ambiguous than describing it in prose. **Planning
Mode** (`/plan`, or `Shift+Tab` twice) has Claude research broadly across
the project before proposing a detailed plan and waiting for your
approval — genuinely useful for tasks needing broad codebase context or
touching multiple files, and you can even open the plan in your own
editor (`Ctrl+G`) to hand-edit it before approving.

**Effort level** (`/effort`) is a separate dial from Planning Mode,
controlling how much a single request reasons before answering — low is
faster and cheaper, max reasons longest on hard problems, with the
default depending on your specific model and plan. The keyword
`ultrathink` in a single prompt signals extra reasoning for that one turn
without changing the session's overall effort setting. Planning Mode suits
tasks needing *breadth* (multi-file, multi-step); a higher effort level
suits tasks needing *depth* (a hard logic or debugging problem) — they
compose for tasks that genuinely need both, at the cost of more tokens
either way.

## Controlling the flow of a long conversation

Beyond `/compact` and `/clear` (covered in Module 1), three more precise
controls matter for a session that's drifting:

- **Escape** interrupts Claude mid-response — useful the moment it starts
  tackling more than you actually asked for, so you can redirect before it
  goes further down the wrong path.
- **Escape twice, or `/rewind`**, jumps back to an earlier point in the
  conversation, letting you discard a debugging detour's noise while
  keeping the codebase understanding Claude built up getting there.
- Combining **Escape + `/memory`** is the concrete fix for a repeated
  mistake: stop the response, write the correct approach directly into
  `CLAUDE.md`, then continue — so the correction survives past this one
  conversation instead of needing to be repeated every time.

## Custom commands

A custom command lives at `.claude/commands/<name>.md` — the filename
becomes the command (`audit.md` → `/audit`), picked up automatically with
no restart needed. Commands accept a `$ARGUMENTS` placeholder for
flexibility (`/write_tests the use-auth.ts file in the hooks directory`),
turning a repeatable, project-specific workflow (a dependency audit, a
test-writing convention, a deploy sequence) into one reusable invocation
instead of a re-typed multi-sentence request every time.

## Extending with MCP servers: a concrete example

Beyond the conceptual MCP coverage in Module 1, this course walks a real
example: the **Playwright MCP server** (`claude mcp add playwright npx
@playwright/mcp@latest`) gives Claude control of an actual browser —
letting it navigate to a running app, generate a component, *see* the
real visual output (not just the code), and revise a generation prompt
based on what it actually observed rendered. Pre-approving a server's
tools (adding `mcp__playwright` to the `allow` array in
`.claude/settings.local.json`) avoids a permission prompt on every single
tool call once you trust it.

## GitHub integration

`/install-github-app` sets up Claude to run inside GitHub Actions,
generating a PR that adds two default workflows: a **mention** action
(tag `@claude` in any issue or PR; Claude plans and executes with full
codebase access, replying in place) and a **pull request** action
(automatic review, impact analysis, and a posted report on every new PR).
Both are customizable afterward — adding setup steps, custom instructions
describing your project's running state, and MCP server configuration.
One sharp edge worth knowing: **GitHub Actions has no equivalent of local
permission shortcuts** — every tool from every MCP server must be
explicitly listed in `allowed_tools`, unlike local development where you
can pre-approve a whole server at once.

## Hooks, in more depth

A hook intercepts the normal request → tool-call → execution flow at a
specific point. **PreToolUse** hooks run *before* a tool executes and can
actually block it; **PostToolUse** hooks run after (so they can't block,
but can trigger a follow-up action or feed Claude additional information).
Your hook command receives the proposed tool call as JSON on stdin (tool
name, input parameters) and communicates back purely through its **exit
code**: `0` proceeds normally, `2` blocks the call (PreToolUse only) with
your stderr output relayed to Claude as the reason. Beyond these two,
several more hook events exist — **Notification**, **Stop**,
**SubagentStop**, **PreCompact**, **UserPromptSubmit**, **SessionStart**,
**SessionEnd** — each receiving a differently-shaped stdin payload. A
genuinely useful debugging trick from the course: point a hook's command
at `jq . > post-log.json` temporarily, so you can inspect exactly what
JSON a given hook actually receives before writing real logic against it.

Two concrete hook patterns worth internalizing: a **PostToolUse type-check
hook** that runs the compiler after every edit and feeds any errors
straight back to Claude — catching the common failure where Claude
updates a function signature but misses a call site elsewhere in the
project; and a **duplication-prevention hook** that, on edits to a
sensitive directory (like a shared queries folder), spins up a *second*,
separate Claude Code instance specifically to review the change for
functionality that already exists elsewhere — a heavier pattern (real
added latency and token cost), best reserved for the specific directories
where consistency actually matters most.

One practical sharing gotcha: hook scripts should use **absolute paths**
(a documented security recommendation, guarding against path-interception
attacks), which makes a checked-in `settings.json` awkward to share across
different machines. The fix pattern: commit a `settings.example.json`
with a `$PWD` placeholder, and have a setup script substitute the real
absolute path per-machine into a generated `settings.local.json`.

## The Agent SDK — running Claude Code from your own code

The **Agent SDK** (`@anthropic-ai/claude-agent-sdk` — not the similarly
named `@anthropic-ai/claude-code`, which is the CLI itself) gives you the
same agent loop the CLI runs — file reading, editing, tool use — callable
programmatically from your own TypeScript or Python application. A minimal
call streams back the same JSON message events you'd see in the CLI's own
output (tool calls, tool results, text), and `allowedTools` restricts the
tool set available to a given call, the SDK's equivalent of the CLI's
`--allowedTools` flag. Everything else this module covered — custom
system prompts, MCP servers, hooks, subagents, session resumption — is
available through the SDK too, for anyone building their own tooling on
top of Claude Code rather than using the CLI directly.
